# 关灯科技二轮实战：准备与限时安排

## 已知规则

依据原始邀请及正式考前规则：点击“开始”才显示任务书并开始 30 分钟计时，服务器时间不会因刷新或换设备重置；输入为业务目标与发放的 CSV；需要自行判断最有价值的部分和如何证明有用；技术栈与工具不限，鼓励 AI。

交付为公开 GitHub 仓库，**仓根 README.md 与 AI_LOG.md 均必需**。README 写清“我的判断、做了什么、怎么证明有用”，数字必须能由发放数据复算。AI_LOG 记录关键提示词、AI 错误与实际修正。作答期间无人答疑，未明确的口径自行判断并写入 README。

30 分钟后有 5 分钟不算迟交的宽限。开始后 48 小时内可多次提交，但主评分采用时限内（含宽限）、且开始追问前的最后一次提交；后续优化作为持续优化评估。每次先推送，再在任务页提交地址；后续推送必须重新提交地址才计入。

首次提交约 1 分钟后会显示 2–4 个追问。开始任务后 48 小时内可自行选择开始追问，开始后限时 12 分钟且到点自动交卷。开始追问会固定评分版本，先完成想计入的修改和再次提交。

具体业务与任务数据尚未收到。下面的时间安排和实现建议不预设评分权重，也不规定只能交统计报告或必须采用某种前后端框架。

## 使用当前项目

修正版在当前“关灯科技面试题目”项目的 `exam-kit/`，与项目内其他模板并列。Git 身份、GitHub 凭据和代理沿用项目根目录已经验证的配置。不要整体复制其他工具目录中的 `.git`。

从项目根目录进入：

```bash
cd exam-kit
bash run.sh --test
bash run.sh --file data/sample_orders.csv --open
```

环境信息以本次实际检查和 `out/metrics.json` 为准，不把某个会话的 PATH 状态当作永久事实。启动脚本优先使用本地 `.venv`，没有兼容环境时按 README 安装。页面离线查看不需要 Python，重新计算需要依赖。

Git 预检在项目根目录执行：

```bash
git config --local --get user.name
git config --local --get user.email
git status --short
git remote -v
```

本项目已有真实推送验证记录。正式使用前确认现有代理正常；不需要在准备工具目录重复创建并删除测试仓库，也不要改全局 Git 身份。

## 拿到任务后先定义问题

先回答：使用者要作什么决策？每行是什么？主指标如何计算？用什么参照证明价值？

- 提升复购：定义用户、首购队列、复购窗口和观察期是否完整；订单金额不能替代复购率。
- 降低成本：明确成本是否为总额还是单位成本，指定越低越好；同时核查服务质量等约束。
- 找问题或异常：明确错误规则、对照样本、误判成本和可核查明细。
- 提升效率或构建工具：验证任务完成率、关键流程和节省的步骤；按题目选择是否需要交互页面或后端。

工具默认选择只帮助浏览字段。确认后用 `--metric`、`--group`、`--date`、`--entity` 固定口径；标题仅作展示。需要派生指标时，写清转换逻辑并保留原始数据。

## 30 分钟建议分配

| 时间 | 工作 | 完成判据 |
|---|---|---|
| 0–4 分钟 | 读正式任务与规则，定义目标、指标、交付形式 | 一句话目标和明确口径 |
| 4–8 分钟 | 检查 CSV、缺失、重复、时间覆盖与数据粒度 | 确认一个能验证的切入点 |
| 8–20 分钟 | 实现核心计算或最小可用流程 | 核心功能能跑，结果能复核 |
| 20–25 分钟 | 核验关键数字、参照方案和限制 | 手工小样本或独立算法复核；必要的业务复核 |
| 25–28 分钟 | 完善仓根 README、AI_LOG、复现命令和公开仓库 | 数字来自发放数据，链接可访问 |
| 28–30 分钟 | 提交并检查回执 | 留出网络和提交缓冲 |
| 30–35 分钟 | 紧急宽限 | 处理故障并完成提交，建议不作为计划开发时间 |

把范围控制在一个核心问题上，允许使用支撑该问题所必需的表、图或功能。交付形式服从正式任务；这份探索工具只是其中一种基础能力。

## 怎样证明有用

同时给出适合任务的参照、绝对数值、变化幅度、样本量、业务约束和验证边界。例如从 10% 到 12%，是增加 2 个百分点、相对提升 20%。

历史分组均值差异不能直接表示增加预算或改变流程后的收益。没有实验或有效识别设计时，可以交付观察发现、明确的待验证假设和后续验证方案。

Welch 检验只在比较对象预先明确且行间独立时适用；重复用户订单不能直接当独立样本。本工具默认不计算 p 值，具体启用条件见 README。不要通过不断换指标和分组寻找显著结果。

时间切片为描述性检查；“未见翻转”不证明稳定，样本不足必须写“无法判断”。成本需要数值和口径才能进入净收益，缺少数据时应明确不可测。

## 交付前检查

1. 核心指标和展示标题确实对应业务问题；至少手工复算一个关键数字。
2. 命令、依赖、数据校验值和运行目录写清，结果能复现。
3. `index.html` 与 `out/metrics.json` 来自本次成功计算；截图若引用，另行生成并检查。
4. 正式业务结论只引用发放数据；人工示例和测试数据明确标注。核对公开范围和 Git 待提交清单。
5. 仓根 README 包含“我的判断、做了什么、怎么证明有用”；仓根 AI_LOG 记录真实关键交互，并区分考前准备与正式作答。
6. 在项目根目录使用已验证的提交配置，先推送再提交仓库地址，检查公开访问与提交回执。之后再推送，必须再次提交地址。
7. 开始追问前确认希望计入的版本已经提交。12 分钟追问可另选时间，但须在任务开始后 48 小时内启动；具体状态以页面显示为准。

## 追问准备

准备解释自己的实际选择，不背诵固定结论：

- 为什么这个指标能回答业务目标？分母和观察单位是什么？
- 为什么选这个切入点？舍弃其他方向的成本是什么？
- 数据有哪些缺失、重复和异常？具体如何影响结果？
- 什么是已验证结果，什么仍是历史关联或假设？
- 如果换时间、分群或成本口径，判断可能怎样变化？
- AI 做了哪些工作？自己怎样复核？
- 多给两小时，按优先级补哪几项验证？
