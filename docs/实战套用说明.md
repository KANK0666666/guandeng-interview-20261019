# 正式实战：拿到题目后怎么套

这份说明服务于 30 分钟开发和后续追问，已按 2026-10-19 用户提供的正式考前规则更新。模板里的订单与库存数据是人工演示，只能用于功能检查，不能作为正式业务结论依据。

## 必须交付的内容与时间规则

- 公开 GitHub 仓库；仓根 `README.md` 必须写明“我的判断（看到了什么、根问题是什么）、做了什么、怎么证明有用”。数字必须能由发放数据复算，附可复现脚本或步骤。
- 仓根 `AI_LOG.md` 必须记录关键提示词、AI 哪里不对、实际怎样修正。已有考前记录，正式作答时继续追加；不得虚构人工修改或核验。
- 仅使用发放的数据作业务结论依据。自己补造的示例或测试数据须标注，并与业务证据区分。
- 作答期间无人答疑；不明确的口径自行判断并写进 README。
- 点击“开始”才计时，服务器计时不会因刷新或换设备重置。30 分钟后有 5 分钟宽限，超过宽限标记迟交；建议仍在第 30 分钟前交付。
- 任务开始后 48 小时内可多次提交。主评分采用时限内（含宽限）、且开始追问前的最后一次提交；后续优化按规则纳入持续优化评估。
- 先推送代码再提交仓库地址。每次提交记录当时的仓库状态；继续推送后须再次提交地址。
- 首次提交约 1 分钟后出现 2–4 个追问。在开始任务后 48 小时内选择开始追问，开始后限时 12 分钟。开始追问会固定评分版本；先完成想计入的修改、推送和再次提交。

## 点击开始前

- 运行 `npm run dev`，确认三套模板都能打开。
- 保留当前依赖和已验证代码，确认 `npm run check:all` 通过（包含 `exam-kit`）。
- GitHub 提交环境已配置；正式公开仓库 [guandeng-interview-20261019](https://github.com/KANK0666666/guandeng-interview-20261019) 已创建并关联当前项目的 `origin`，公开访问和推送权限已验证。考前仅创建空仓库，正式作答后再推送交付版本。
- 规则页可先阅读；以页面的“开始”按钮为计时触发点，准备完成后再点击。

拿到任务书和 CSV 后，先保存任务书全文与数据文件到 `private-inputs/`；这个目录默认不进 Git。分析工具可直接读取原文件绝对路径：

```bash
npm run analyze -- --file "$PWD/private-inputs/任务数据.csv"
# 确认字段后补上 --metric 指标列 --group 分组列 --entity 实体列
```

先用分析工具核对数据，再按目标选择交互模板；若任务只要求分析报告，可直接使用 `exam-kit/index.html` 与 `exam-kit/out/metrics.json`。报告产物默认不进 Git；作为正式交付时，核对后明确加入所需文件，例如 `git add -f exam-kit/index.html exam-kit/out/metrics.json`。

## 30 分钟建议分配

| 时间       | 产出             | 具体动作                                                           |
| ---------- | ---------------- | ------------------------------------------------------------------ |
| 0–4 分钟   | 一句话业务目标   | 读任务书；确认目标用户、要作的决定、交付要求；查看 CSV 表头与样本  |
| 4–7 分钟   | 一个主模板       | 判断是分析、管理还是规则核查；选模板、映射字段，明确空值和分母口径 |
| 7–20 分钟  | 一个完整业务闭环 | 补最关键的规则/排序/指标，让用户能从证据走到行动；删除无关展示     |
| 20–24 分钟 | 可复核的证据     | 人工核对至少一个汇总和一条记录；跑检查；试一次导出和刷新           |
| 24–28 分钟 | 公开可运行仓库   | 完成仓根 README 与 AI_LOG，提交代码并推送；检查公开访问和复现命令 |
| 28–30 分钟 | 提交与缓冲       | 按任务书提交仓库地址，留出网络和表单问题的处理时间                 |
| 30–35 分钟 | 紧急宽限         | 仅作故障和提交缓冲；规则允许宽限内提交不算迟交                    |

时间分配可以调整；优先保住能跑、算对、能解释的一条闭环。

## 选择模板

先填一句话：**“帮助［使用者］根据［证据］决定［行动］。”**

- 用户需要看整体情况、比较对象：选择 A，重点修改指标、分组、趋势与解释。
- 用户需要定位记录、跟进处理：选择 B，重点修改字段、状态和业务操作。
- 用户需要找出超时/不足等明确条件：选择 C，重点修改规则、排序和核查证据。

```bash
npm run template -- overview
# 或 records / diagnostics；all 可恢复全部入口
```

改 `project.config.ts` 的名称、标题、说明和 `templateMode`。新 CSV 的字段映射先在页面操作验证，再按实际要求决定是否固化默认值。

## 常见改动的位置

| 要改什么                             | 文件                                                    |
| ------------------------------------ | ------------------------------------------------------- |
| 品牌、标题、显示哪些页面             | `project.config.ts`                                     |
| CSV 列的清洗、日期、百分比、单位换算 | `server/data.mjs`，按真实数据新增明确转换               |
| 指标口径、分组、时间序列             | `summarize()` 与 `src/views/Overview.tsx`               |
| 检索、排序、状态与额外动作           | `pageRows()`、`server/app.mjs`、`src/views/Records.tsx` |
| 业务规则与命中排序                   | `diagnose()` 与 `src/views/Diagnostics.tsx`             |
| 数据库或持久化字段                   | `server/store.mjs`                                      |
| 视觉细节                             | `src/styles.css`                                        |

不要为了套模板把真实字段强行解释成订单、金额或风险。没有日期字段就省略趋势；只有类别数据就从计数开始。不能计算的指标明确省略。

## 交付 README 的内容骨架

正式交付时，将仓根 README 从“模板说明”改为本题答卷，并保留必要运行步骤。建议使用以下结构：

1. **我的判断**：从发放数据看到了什么，根问题是什么；目标用户与决策是什么；依据和假设是什么。
2. **做了什么**：选择的功能、计算或规则，以及实际取舍。
3. **怎么证明有用**：业务指标与参照、具体数字、复算命令、明细证据、验证范围与限制。
4. **数据与口径**：文件来源和校验值、字段、有效样本、分母、时间窗口、缺失处理；标明人工测试数据并排除其业务用途。
5. **如何复现**：环境版本、安装、运行、构建和复算步骤；说明如何取得发放数据并放到指定位置。
6. **局限与下一步**：已经完成什么、没有证明什么、下一项最有价值的验证。

在 README 中链接仓根的 `AI_LOG.md`，不能用一段简短 AI 使用声明替代该文件。关键业务数字可用“结论 → 原字段与筛选条件 → 计算脚本/命令 → 输出位置”的方式逐条建立对应关系。

## GitHub 提交

正式仓库已关联为 `origin`，无需再次创建。先检查追踪文件，避免把本地数据库或未获准公开的任务材料一并提交。

```bash
test -s README.md && test -s AI_LOG.md
git status --short
git add .
git commit -m "Deliver task-specific MVP"
git push -u origin HEAD
```

网络如需代理，沿用当前已配置的 GitHub 专用代理。完成后在未登录环境或公开网页确认仓库可访问，仓根两个文件都能读到，README 的命令可复现，再在任务页面提交地址并确认回执。

只推送 GitHub 不等于更新任务页的提交。任何希望计入的后续修改，都重复“推送 → 提交地址 → 确认回执”，记录当次提交 SHA 和页面状态。开始追问前再确认版本；不要把 48 小时窗口误当成 48 小时不迟交。

## 追问准备

围绕实际交付回答，不背模板答案：

- 为什么选这个业务问题，而不是另一个？
- 这条结论对应哪些数据和口径？
- 空值、异常格式、重复记录怎么处理？
- 前后端各负责什么，持久化保存了什么？
- 哪些代码来自 AI，你怎样验证？
- 如果数据量增加或多人使用，最先改哪里？
- 再给一天，你会优先补什么，为什么？
